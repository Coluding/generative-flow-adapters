Lesson 01 · Sharding pipelines

Finding the global coupling

Before you split a preprocessing stage across 18 machines, one question decides everything. This lesson teaches you to ask it — and to recognise the three shapes the answer takes.

The one idea

A stage is shardable if and only if every output depends only on the inputs inside its own shard. Anything that depends on all the data is a global coupling, and it cannot be distributed — it can only be deferred to a merge step that runs once, over everything.

This is the map / reduce split, and it is older than any of our tooling: Dean & Ghemawat formalised it in 2004 precisely because "which part of this can run independently?" is the question that decides whether a job takes 21 hours or 80 minutes.

The RT-1 conversion in this repo is a worked example. Converting one episode — decode its frames, write episode_i.mp4, stack its 7-dim actions — touches nothing outside that episode. Pure map. But the converter also does this (convert_rt1_to_mp4meta.py:93):

alla = torch.cat([e["actions"] for e in meta], dim=0)   # every episode
mean = alla.mean(dim=0); std = alla.std(dim=0).clamp_min(1e-6)
e["actions"] = (e["actions"] - mean) / std

That mean is a function of all 87,212 episodes. Eighteen shards would each compute their own — eighteen different action scales, silently. So the shards run with --no-normalize, and the normalization moves to merge_rt1_shards.py. That single decision is the sharding strategy; everything else is bookkeeping.

The three shapes a coupling takes

In practice couplings are not exotic. Nearly all of them are one of three, and RT-1 happened to contain all three at once:

ShapeTest: does it need the whole set?RT-1 instanceResolution
Statistic An aggregate — mean, std, min/max, vocabulary, dedup set Per-dim action mean/std Shards emit raw values; merge computes once and applies
Identifier A counter or key that must be unique across the corpus clip_id = f"rt1_{i}" — restarts at 0 in every shard Merge reassigns a global running index
Ordering Meaning attached to an item's position, not its content episode_idx is part of the latent cache key Fix a deterministic concatenation order; never re-derive it casually

Notice the asymmetry in how they hurt. A missed statistic gives you 18 inconsistent scales. A missed identifier gives you 18 clips all claiming rt1_0 — and since the caption table is keyed on clip_id, the frozen base would be conditioned on the wrong instruction for thousands of clips. A missed ordering assumption means a stale latent cache silently serves you another episode's latents.

None of these three crashes. Every one of them produces a pipeline that runs to completion and yields a loss curve that goes down. That is the whole reason this lesson exists: sharding bugs are not caught by "did the job succeed?" — they are caught only by the audit you do beforehand, and by guards you write into the merge.

The audit

Three questions, in order, against any stage you are about to shard:

  1. Statistic? Does any output value require reading records outside this one? (Grep for .mean(, .std(, set(, Counter, sort, min/max.)
  2. Identifier? Does the stage allocate names, indices, or keys that something downstream looks things up by?
  3. Ordering? Does anything downstream depend on where a record sits rather than what it contains?

If all three are "no", shard it. If any is "yes", that piece moves to the merge — and the merge should refuse to run when its assumptions are violated, rather than quietly producing a short or mis-keyed dataset. Ours does:

if "action_mean" in e or "action_std" in e:
    raise SystemExit(f"{mp} is ALREADY normalized ... must be --no-normalize")

Retrieval practice

Answer from memory before reading the feedback — the effortful retrieval is what makes this stick, not the recognition. Items are deliberately mixed across datasets.

SHARD-SAFE = each output depends only on its own shard. GLOBAL-DEP = has a global coupling; must be deferred to a merge.

1. ACWM-Phys: encode each 17-frame window to Wan VAE latents and write it to the cache.

2. OpenVid: build a caption vocabulary, dropping tokens that appear fewer than 5 times across the corpus.

3. RT-1: T5-encode one episode's natural_language_instruction into a context tensor.

4. Any dataset: assign each clip to train/val by hash(clip_id) % 100 < 1.

5. Any dataset: assign the first 1% of episodes to val, the rest to train.

6. RT-1: drop episodes shorter than the 17-frame window (ep.length >= span).

One nuance worth carrying

Sharding by split slice — train[0:4846], train[4846:9692], … — guarantees the shards partition the dataset: every example appears exactly once. It does not, on its own, guarantee the order examples come back in. TFDS is explicit that example order is only guaranteed for a fixed value of the interleave args, and that ds.take(x) and split='train[:x]' are not equivalent.

For RT-1 the order is preserved — verified, not assumed: the first 2,572 episodes of the sharded run match the single-pass run caption-for-caption and length-for-length. That matters because episode_idx is baked into the latent cache key (see the reference sheet). Fine here; something to re-verify on the next dataset.
